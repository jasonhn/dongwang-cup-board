# 内战光荣榜执行标准（统计口径与数据采集）

本文只回答一件事：**一场比赛算不算进看板、一个人的胜/负怎么记、什么情况下可以把它去掉、谁能改这些规则**。排名公式不在本文，见 [`docs/排名算法.md`](排名算法.md)。

制定这份标准的原因：排名公式本身只有一个写死在代码里、并由测试钉死的群规常数对（赢一局 `+50`、输一局 `−35`，见 [`docs/排名算法.md`](排名算法.md) §6），如果「哪些比赛算数」还靠人现场判断，那榜单就仍然是人工决定的。所以本文的规则全部写成**机械可判定**的形式：要么由代码自动判定并留痕，要么由登记人在登记时把结论写进仓库文件里，事后任何人都能复核。**凡是本文没有写明的情况，一律按「不改动、不补数、不猜测」处理**——宁可榜上少一场，也不手工加一分。

文中的代码引用一律写**文件 + 函数名／字段名**而不是行号（代码会继续改，行号会漂，函数名不会）。所有数值是当前快照 [`site/data/league.json`](../site/data/league.json) 的读数：18 场、39 人、180 人次、联赛 ID 19905。

## 0. 三条总原则

| # | 原则 | 由什么保证 |
|---|---|---|
| 1 | **数据只能由代码产生。** 任何人（包括群主）都不能在页面上或 JSON 里手工改胜负。 | `site/data/*.json` 是 CI 产物，每次刷新会被整体覆盖并提交回 `main`（[pages.yml](../.github/workflows/pages.yml) 的 `Persist refreshed data` 一步） |
| 2 | **排除只能用两个配置字段表达**，且每条排除都要留下 `match_id` + 原因，任何人可核对。 | `exclude_game_modes`、`exclude_match_ids`（[collector.py](../collector.py) 的 `load_config()`），留痕在 `_build_payload()` 写的 `metadata.excluded_matches` |
| 3 | **人工输入只有两个通道**：`names.json`（昵称映射）与 `overrides.json`（国服补录）。两者都进仓库、都要留痕、都只影响显示或补缺，不允许用来改胜负。 | `load_display_names()`、`load_match_overrides()` |

## 1. 统计口径的数学定义

### 1.1 记号

| 记号 | 含义 | 由哪段代码决定 |
|---|---|---|
| `M` | 快照里已收录的比赛集合，按 `(start_time, match_id)` 升序 | [collector.py](../collector.py) 的 `_order_matches()` |
| `[T₀, T₁]` | 页面上选定的时间窗 | [app.js](../site/app.js) 的 `render()` |
| `M_T` | `M` 中 `start_time ∈ [T₀, T₁]` 的场次，也就是当前这张表统计的比赛 | `render()` 里的时间过滤 |
| `R(m)` | 场次 `m` 的**可归属阵容**：`account_id` 为正整数且 `player_slot ∈ {0..4} ∪ {128..132}` 的位置 | 写入时由 `normalise_match()` 过滤，统计时由 `getVisiblePlayers()` 再过滤一次 |
| `side(p)` | 该位置所在阵营：`player_slot < 128` 为天辉，否则夜魇 | `calculate()`（`isRadiantSide()` 用同一条判据） |
| `W(m)` | 该场胜方：`radiant_win` 为真则天辉，否则夜魇 | `calculate()`；采集时 `normalise_match()` 强制 `radiant_win` 必须是布尔，否则整场拒绝 |
| `w_i, l_i, n_i` | 选手 `i`（由 `account_id` 唯一确定）在当前窗口内的胜场、负场、总场数 | `calculate()` |
| `p̂_i = w_i / n_i` | 表格里显示的真实胜率 | `renderStats()` 里的 `makeRateCell(player.wins / player.total)` |
| `a`, `b` | 群规的两个数字：赢一局 `+a`、输一局 `−b`。本群取 `a = 50`、`b = 35`（最简比值 `10 : 7`） | `site/app.js` 的 `POINTS_PER_WIN`／`POINTS_PER_LOSS` |
| `S_i = a·w_i − b·l_i` | **联赛积分**，排名主键，也是表里的「积分」这一列 | `pointsOf()` |

### 1.2 胜负归属的定义

对 `m ∈ M_T` 与 `p ∈ R(m)`：

```
该位置记胜场 1 ⟺ side(p) = W(m)
该位置记负场 1 ⟺ side(p) ≠ W(m)

w_i = |{m ∈ M_T : ∃ p ∈ R(m), account_id(p) = i, side(p) = W(m)}|
l_i = |{m ∈ M_T : ∃ p ∈ R(m), account_id(p) = i, side(p) ≠ W(m)}|
n_i = w_i + l_i
```

三点必须讲清楚：

1. **按「场上阵营 + 该场最终胜方」记分**，没有任何按 KDA、时长、加入先后判胜负的逻辑。中途退出或后来加入的人，按 OpenDota／补录里那一场的阵容与最终胜方记一局胜负——代码里没有 `leaver` 之类的分支（未实现，见 §8）。
2. **匿名位置不计入任何人。** `account_id` 缺失（对方没开「公开比赛数据」）时该位置被记为 `null`，统计时被直接过滤：`normalise_match()`、`getVisiblePlayers()`、以及体检脚本 [rank_stats.py](../scripts/rank_stats.py) 的 `load()` 三处口径一致。这些位置会计入 `metadata.anonymous_player_slots`（`_build_payload()`）并在页面上提示（`showCoverageNotice()`），**不会伪装成某个已知玩家**。
3. **同一 `account_id` 在同一场出现两次会被计成两局**（代码里没有同场去重，见 §8）。目前快照里不存在这种情况。

### 1.3 命题 1（守恒式，口径自检的依据）

**前提 P1**：每场 `m ∈ M_T` 的可归属阵容里，天辉人数 = 夜魇人数（内战 5v5 且 10 个位置都不是匿名）。

**结论**：`Σ_i w_i = Σ_i l_i`，于是

```
按场数加权的联盟平均胜率 = Σ w_i / Σ n_i = 1/2
积分总量                  Σ_i S_i = (a − b)·Σ w_i = 15 × 90 = 1350
```

**证明**：每场恰好贡献 `|R(m) ∩ 天辉|` 个胜场与 `|R(m) ∩ 夜魇|` 个负场，两者在 P1 下相等，逐场求和即得。∎

这条不是装饰：它是**口径有没有坏掉的检测器**。`Σ胜 ≠ Σ负` 只有两种可能——(a) 某场两队人数不等（阵容不全或有人匿名），(b) 收录了不是两队对打的比赛。两者都应该修口径或补数据，而不是调排名。检测命令与当前读数见 §9。

积分总量那条则要说清语义：`a ≠ b` 时积分**不是零和**（本快照 `ΣS = 1350 > 0`），所以 `S = 0` 只代表盈亏平衡胜率 `35 ÷ 85 = 7/17 ≈ 41.2%`，**不代表联盟中位**（联盟中位是 `p̂ = 50%`）。页面说明必须把这一点写明白，否则群友会把 0 分读成中游。

当前快照读数：18 场全部 `|R(m)| = 10`、两边各 5 人，`Σ胜 = Σ负 = 90`，加权平均胜率 `0.500000`，`anonymous_player_slots = 0`，`incomplete_roster_match_ids = []`。

### 1.4 名次与并列

排序键：`S_i` 降序 → `w_i` 降序 → 昵称（`zh-CN` 字典序）→ `account_id` 升序（`comparePlayerRanking()`）。后两级只做**显示顺序**用：`S_i` 与 `w_i` 都相等时 `l_i = (a·w_i − S_i)/b` 也必然相等，也就是战绩完全相同，标准里没有任何东西能区分这两个人，所以给出**同一个名次（并列）**，而不是让昵称字典序决定谁压过谁（`rankNumbers()`，显示层 `makeRankCell()`）。

比较两个人只用整数，不做除法：

```
S_i > S_j  ⟺  50Δw > 35Δl  ⟺  10Δw > 7Δl  ⟺  17Δw > 7Δn      // Δw = 胜场差，Δl = 负场差，Δn = 场数差
```

同分的结构也是闭式的：`S_i = S_j ⟺ (Δw, Δl) = (7t, 10t)`，也就是**多打 17 场里 7 胜 10 负，积分一分不变**。同分之内胜场多 ⟺ 场数多（`w = (S + 35n) / 85`），所以第二个排序键奖励的正是出勤。**诚实注记**：`gcd(50, 35) = 5`，积分恒为 5 的倍数；本赛季最活跃者只有 14 场，凑不出 17 场的兑换比，所以「不同战绩算出同一个分」暂时不出现，榜上的并列只来自战绩完全相同。

**任何人可以只用表里的两列复现名次**：`积分 = 胜 × 50 − 负 × 35`（也就是表里的「积分」那一列），同积分比胜场数，两列都一样就是并列。这是「统一且客观」的可执行定义——不需要访问代码、不需要内部数据；唯一的常数对 `50 : 35`（最简 `10 : 7`）是公示的群规，写在页面说明、代码与测试三处（见 §6 的变更流程与 [`docs/排名算法.md`](排名算法.md) §6）。

## 2. 内战认定：三条收录路径与其判定条件

`config.json` 的 `collect_mode` 决定用哪条路径（`collect_snapshot()`）。当前是 `"league"`。

| 模式 | 比赛从哪里来 | 是否校验「属于本联赛」 | 口径含义 |
|---|---|---|---|
| `league` | OpenDota `GET /leagues/<id>/matchIds`（`collect_league_data()`） | **校验**：`leagueid ≠ league_id` 的场次会被 `normalise_match()` 拒绝，这场不会进看板，而是记进 `metadata.unavailable_matches` | 认定标准 = 这场比赛带懂王杯的联赛标记 |
| `tournament` | Valve `IDOTA2Match_570/GetMatchHistory?league_id=`（`SteamMatchClient.tournament_match_ids()`），再交给 OpenDota 逐场解析 | 校验，但 `leagueid = 0` 视为「未知」并接受（`normalise_match()` 的 `accept_unknown_league`，该模式下为真） | 认定标准 = Valve 把这场比赛列在本联赛下。用于 OpenDota 把联赛标成 `tier: "excluded"` 的情况 |
| `manual` | `matches.txt` 里人工登记的 `match_id`（`read_manual_match_ids()`） | **不校验**（`collect_manual_data()` 传 `expected_league_id=None`） | 认定标准 = 登记人按 §2.1 的核对清单核对过，并把结论写进注释 |
| `both` | 联赛归集 + 未重复的登记场次（`collect_snapshot()`） | 联赛部分校验；补登记部分不校验 | 混合，同一个 `match_id` 不会抓两次 |

`tournament` 模式另有两条口径细节，写在这里以免将来误以为「数据被删了」：一次最多导入 `max_tournament_matches` 场（默认 100，超出时保留最新的）；**已经进过快照的场次不会因为超出上限而被移除**（`collect_tournament_data()` 里的 `known_ids`）。

### 2.1 人工登记前的强制核对清单

`manual`／`both` 模式下，把 `match_id` 写进 `matches.txt` 之前必须核对，并把结论作为注释行写进同一个文件（注释会被解析器忽略，但会永久留在仓库里供人复核——`read_manual_match_ids()` 只取 `#` 之前的内容）：

1. **这场比赛是不是内战**：`leagueid` 是否等于本联赛 ID；或十人名单是否全部属于本群。
2. **是不是 5v5**：不是 solo／游廊／单人房间。
3. **是不是 match_id**：客户端显示的房间号（lobby id）不是 `match_id`。

仓库里已有的两次真实处理就是这条标准的判例，都写在 [matches.txt](../matches.txt) 的注释里：

- 2026-11-12：清掉三场手动登记的普通房间（两场 turbo + 一场游廊），因为 `leagueid` 都是 0 → 不符合「带联赛标记」，不算内战。
- 2026-11-15：撤掉误登记的三场（9089282128、9089311300、9089358279）。它们是 5 黑组队列队（`lobby_type 7`、`leagueid 0`），天辉方每场都是五个不同的路人，十个人里只有一个是懂王杯的 → **不是内战，一场都不算**。

**规则**：登记一场外场时，若 `leagueid ≠ 本联赛`，则要求**十人名单全部是本群成员**才可计入；两者都不满足就不登记。这条判定由登记人做，但结论必须以注释形式留在文件里，任何人可以对着 OpenDota 原页复查。

## 3. 排除规则：只有两个字段，且必须留痕

任何一场比赛要从榜上去掉，只能用下面两条通道表达。**不允许**在代码里写一次性的 `if`，不允许「某场只不算某一个人的分」，不允许直接编辑 `site/data/*.json`。

| 通道 | 生效时机 | 留痕 |
|---|---|---|
| `exclude_game_modes`（默认 `[21]`，即 Valve 的 1v1 solo 房，`DEFAULT_EXCLUDE_GAME_MODES`） | 解析到比赛数据之后（`_collect_matches()` 里的 `skipped()`）。对**缓存里的历史场次同样生效**，不只是新抓的场次 | `metadata.excluded_matches` 里记 `match_id` + `game_mode N 不是内战（solo 房间）` |
| `exclude_match_ids` | **发请求之前**就拦掉（`_collect_matches()` 开头），省 API 额度 | `metadata.excluded_matches` 里记 `match_id` + `config exclude_match_ids` |

两个字段都会被 `_int_list()` 规范化成「排序去重后的整数列表」，非数字直接报错，所以不存在「拼错一个 ID 就静默少算一场」。

**这条设计带来一个重要的性质**：口径变更会自动、均匀地作用于全部历史数据。比如把某个 `game_mode` 加进黑名单，它对该模式的所有历史场次一律生效，不会出现「上半年算、下半年不算」这种半途修改。反过来说，**这也意味着排除是不可选择的**：整场对所有人一起排除，不能只对某个人排除。

当前快照里唯一一条排除记录，任何人都能核对：

```json
{"match_id": 9085825973, "reason": "game_mode 21 不是内战（solo 房间）"}
```

这场是从联赛房间开的 1v1，虽然带联赛标记，但不是内战。核对方式：打开 <https://www.opendota.com/matches/9085825973>。

### 3.1 手工补录（完美世界服务器）是唯一的例外通道

在**完美世界服务器**打的比赛，Valve 全球接口和 OpenDota 都查不到，只能靠 `overrides.json` 照抄电竞 APP 里的数据（`load_match_overrides()`）。它必须同时满足：

1. 字段齐全：`match_id`、`start_time`（Unix 秒）、`duration`、`radiant_win`、10 名选手的 `account_id` / `player_slot` / `hero_id`。补录条目会走 `normalise_match()` 同一套校验，缺字段直接报错而不是静默通过。
2. 留痕：补录场次会进 `metadata.manual_override_match_ids`（`_build_payload()`），采集时还会打印一行清单（`main()`）。当前为 `[]`，也就是**本看板目前没有任何手工数据**。
3. 缺 `account_id` 的位置按匿名处理，不计入任何人。

必须知道的两个副作用（都是代码的真实行为，不是建议）：

- 补录场次**无条件优先**于 OpenDota 返回的内容，并且会把该场从 `unavailable_matches` 和 `excluded_matches` 里清除（`_collect_matches()` 末尾）。因此**禁止**用补录去覆盖一场 OpenDota 已经正常解析的比赛——那等于人工改数。
- 补录条目里没有 `game_mode`，`normalise_match()` 会把它记为 `0`，所以**不受 `exclude_game_modes` 约束**。这也是补录必须逐场核对的原因之一。

## 4. 身份与昵称

| 问题 | 口径 | 代码 |
|---|---|---|
| 身份主键 | `account_id`（Steam 64 位 ID − `76561197960141072`）。所有统计按它聚合，改名、改头像都不影响统计 | `calculate()` 以 `accountId` 为 Map 的键 |
| 昵称来源 | `names.json` 的群昵称优先；没有则用 Steam 昵称；再没有则显示 `Account <id>` | `calculate()` 里的 `display_name \|\| personaname \|\| Account …`；写入侧是 `normalise_match()` 与 `_apply_names()` |
| Steam 改名 | 没有配置群昵称的人，显示名跟随**最近一场**的 Steam 昵称；有群昵称的人不受影响 | `calculate()` 里的 `latestStart` 分支 |
| `names.json` 的约束 | 键必须是数字 `account_id`，否则整份文件报错；值会被截断到 40 字 | `load_display_names()` |
| 一个人有多个 Steam 号 | **视为两个人**，各自独立统计。不做同名合并、不做跨号累加 | 由 `account_id` 主键保证 |
| 两个人共用一个号 | 视为同一个人（主键就是 `account_id`）。要拆开只能各自用自己的号打 | 同上 |
| 「同一 `account_id` 在同一场出现两次」 | 目前会被计成两局，**没有检测** | 见 §8 |

唯一允许的人工判断就是 `names.json` 的「`account_id` → 群里叫什么」映射：它只改显示，不改任何计数。新增或修改时在 PR 里写清这个人是谁（当前仓库里只有一条：`129964895 → "Monkey see Monkey do"`）。

## 5. 采集与刷新：谁能动、动完会发生什么

- **触发方式**：push 到 `main`（限定路径，含 `collector.py`、`config.json`、`names.json`、`matches.txt`、`overrides.json`、`site/**`）、每 15 分钟一次 schedule、或手动 Run workflow（[pages.yml](../.github/workflows/pages.yml) 的 `on:` 段）。注意 GitHub 的定时触发会被限流，实际频率低于每 15 分钟。
- **CI 顺序**：`Run collector tests`（`python -m pytest -q`）→ `Refresh OpenDota league data`（跑 `collector.py`）→ `Persist refreshed data`（把 `site/data/*.json` 提交回 `main`）→ 部署 Pages。所以：测试不过 → 不刷新、不部署；手工改的 `site/data/*.json` → 下一次刷新被覆盖。
- **历史场次的稳定性**：`refresh_recent`（默认 5）只重抓最近 N 场，其余用仓库里的缓存（`_collect_matches()`）。唯一会让老场次重抓的情况是「缓存里缺 KDA 字段」，而且每场只补一次（`_has_full_roster_stats()`）。也就是说**已经确定的胜负不会被反复改写**，补的只是展示字段。
- **缓存的作用域**：`_load_existing()` 按 `league_id` 匹配，不匹配就整个忽略缓存。换联赛 ID 等于换看板，缓存不会被误用。
- **时间戳语义**：内容没有变化时保留旧的 `generated_at_utc`（`_stable_snapshot_timestamp()`），所以「更新于」不会在数据没变时假装刷新过。
- **取数失败的处理**：限流会等到下一分钟；匿名日额度用尽才切到带 Key 的请求，并有 `OPENDOTA_MAX_PAID_CALLS`（默认 250）上限保护（`OpenDotaLeagueClient._request()`）。取不到的场次记进 `metadata.unavailable_matches`，页面显示「N 场尚未取得公开详情」（`showCoverageNotice()`）——**不猜、不补数**。

**明确禁止的做法**（无论谁提）：

1. 手工给某人加分／减分、把某场从某个人身上单独摘掉。
2. 直接编辑 `site/data/league.json`、`avatars.json`、`heroes.json`。
3. 基于「我觉得」排除一场比赛（代练、借号、状态不好、对手太强）。排除通道只有 `game_mode` 和 `match_id` 两条，且必须整场排除。
4. 给排名加系数（连胜加成、场次权重、出勤权重）。积分规则之外的可调系数会让测试直接失败；`50 : 35` 只能按上面的流程整体改，不允许「这周先按 50 : 30 算」。
5. 改写 `matches.txt` 里已有的登记记录（要撤销就按 §2.1 加一条注释说明理由，就像已有的两条判例那样）。

上线前自检：

```bash
.venv/bin/python -m pytest -q          # 全绿
.venv/bin/python scripts/rank_stats.py # 口径体检通过（见 §9）
```

## 7. 可核对性：任何人都能自己复查

| 查什么 | 怎么查 |
|---|---|
| 某一场的阵容、阵营、最终胜方 | 战报存档里每行都有 `match_id ↗`，直接跳到 OpenDota 原页（`makeMatchDetail()`） |
| 某一场的赛制 | 存档详情里的「赛制」一行，编号对照表是 `GAME_MODE_LABELS`／`gameModeLabel()` |
| 名次是怎么来的 | 表里的「胜」「负」两列代进 `胜 × 50 − 负 × 35` 就是「积分」这一列，也就是排序用的分数；同积分比胜场数；两列都一样就是并列 |
| 某个人的总 K/D/A | 战报存档里每个位置都有 `kills` / `deaths` / `assists`，把当前范围内属于这个 Account ID 的位置分别相加即可复算（`site/app.js` 的 `readKda()`／`formatKdaTotals()`）。缺这三个字段的位置不计入合计但仍计入场次，所以那一列悬停写的「已汇总 n/m 场」就是覆盖数；老快照缺字段时采集端会按 `_has_full_roster_stats()` 补抓一次。这一列不参与排名，改它不会动任何名次 |
| 哪些场次被排除了、为什么 | `site/data/league.json` 的 `metadata.excluded_matches`，或跑体检脚本 |
| 有没有手工数据 | `metadata.manual_override_match_ids`（当前 `[]`） |
| 有没有位置是匿名／阵容不完整 | `metadata.anonymous_player_slots`、`metadata.incomplete_roster_match_ids`；页面顶部的「覆盖提示」也会说 |
| 登记表的历史与理由 | `git log -p -- matches.txt` |
| 快照是怎么变的 | `git log --oneline -- site/data/league.json`（CI 的提交信息固定是 `Refresh league dashboard data`） |
| 本地跑一遍看板 | `.venv/bin/python -m http.server -d site 8080` 后开 <http://localhost:8080>。**不要双击 `site/index.html`**：`file://` 下浏览器禁止读本地 JSON，页面会显示没有数据，这不是采集出问题 |

## 8. 已知的口径缺陷与待补检测（都**未实现**）

下面这些是当前代码的真实行为缺口，在它们被修掉之前，本文如实标注：

1. **同场重复 ID 不去重**：同一 `account_id` 在同一场的 `players` 里出现两次会被记两局。建议加检测：`|{account_id : p ∈ R(m)}| ≠ |R(m)|` 就报错并记进 `metadata`。
2. **排除原因文案写死**：任何被 `exclude_game_modes` 排除的模式，原因都会写成「`game_mode N 不是内战（solo 房间）`」（`_collect_matches()` 里的 `skipped()`）。若将来排除非 21 的模式，这条文案会失真。建议改成按编号取赛制名——但 `GAME_MODE_LABELS` 这张表本身与 README 有一处矛盾（[README.md](../README.md) 把 `game_mode 22` 说成开黑排天梯，这张表却把 22 标成「加速模式」），要先修表再用它。本快照里出现的模式只有 2 和 3。
3. **口径体检不在 CI 里**：`scripts/rank_stats.py` 的体检目前只在本地手动跑（pages.yml 里没有这一步）。建议加一个 CI 步骤：`Σ胜 ≠ Σ负`，或出现新的 `incomplete_roster`／匿名槽位而无说明时，让刷新失败。
4. **补录与自动采集冲突时无条件覆盖**（`_collect_matches()` 末尾的 override 合并）。建议：若该 `match_id` 已被 OpenDota 正常解析，则拒绝补录并报错，避免「用补录改胜负」。
5. **中途换人没有单独口径**：OpenDota 的 `leaver` 一类字段没有被读取；当前一律按「阵容里有这个人 → 记一局胜负」处理。若群里出现大量中途换人，需要先在代码里定义口径（建议：按最终阵营记，与现在一致，但要在本文写明并加测试）。

## 10. 常见争议按口径回答

| 争议 | 口径回答 |
|---|---|
| 「这场是 1v1 顺手开的，别算」 | 自动排除（`game_mode 21`），已留痕，不需要任何人申请或批准 |
| 「这场是我们开黑排天梯打的，算进去吧」 | 排天梯匹配不带联赛标记，`league` 模式收不到。要计入只能人工登记，并满足 §2.1（`leagueid ≠ 本联赛` 时要求十人名单全是本群成员），并把核对结论写进注释 |
| 「某场有人跑了／阵容不全」 | 按已记录的阵容与最终胜方计；匿名位置不计入任何人，不完整场次会列在 `incomplete_roster_match_ids`。**不补分、不猜**，代价是守恒式 `Σ胜 = Σ负` 会被破坏，这正是要修数据而非调排名的信号 |
| 「他换了 Steam 号」 | 视为新人，从 0 场开始；老号的场次留在老 `account_id` 上。不做跨号合并 |
| 「这场他借号打的／是代练」 | 口径不支持基于判断排除。只有 `game_mode`、`match_id` 两条通道，且只能整场排除 |
| 「某人要求把自己某场去掉」 | 不支持局部排除。要排除只能整场，对所有人生效，并写 reason |
| 「OpenDota 抓不到这场」 | 记进 `unavailable_matches` 并在页面提示，不手工编。若确实是完美世界服务器，走 `overrides.json` 补录（§3.1） |
| 「本地打开页面没数据」 | `file://` 被浏览器禁止读本地 JSON，必须用 `python -m http.server -d site 8080`（§7） |
| 「他场次多但胜率低，凭什么排前面」 | 这是排名标准的事，不是口径问题：积分 `= 场数 × (85 × 胜率 − 35)`，场数与质量一起算，盈亏平衡胜率 `35 ÷ 85 ≈ 41.2%`；真实胜率高于这条线的人多打就涨分，低于的人多打会掉分。每局杠杆对所有人恒定 `+50 / −35`，按真实胜率 `p` 算下一局期望增益 `85p − 35`，与场数无关。反过来，「场数多的压过场数少的」也不是无条件：`8 胜 4 负` 要压过 `6 胜 1 负` 需要 `a/b > 3/2`，现在 `a/b = 50/35 = 1.4286`，所以 `6 胜 1 负`（265 分）排在 `8 胜 4 负`（260 分）前面。推导见 [`docs/排名算法.md`](排名算法.md) |
